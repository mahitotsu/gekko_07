# 要件

本ドキュメントは「何を・なぜ実現するか」（目的・動機・要求水準）を記録する。「どう構築したか」（現在のアーキテクチャ）は[architecture.md](architecture.md)、個々の設計判断の根拠・選択経緯は[docs/adr/](adr/)、具体的な業務シナリオは[use-cases.md](use-cases.md)、各サービスの存在意義・業務ルールは[services.md](services.md)を参照。

## 目的

前作gekko_05（OAuth 2.0 Token Exchangeのアプリ層実装によるサンプル）を踏まえ、以下2点を新たに実演する。

1. **Token Exchangeの実装をアプリ層からEnvoyサイドカー（ext_authz）へ移す**。サービスの実装言語やフレームワークに依存しない横断的関心事として切り出せることを、複数言語で実装されたサービス群を通じて示す（言語構成は未定。[backlog.md](backlog.md)参照）
2. **マイクロサービス群にAIエージェントを組み込む**。エージェントの権限をKeycloakのスコープ設計で厳格に制限し（読み取り・提案のみ、実行不可）、最終判断は人間の決定論的な操作でのみ確定させる設計を示す

想定ユースケース：金融の不正検知・口座凍結。AIエージェントが取引パターンから凍結を提案し、アナリストが確認の上で確定操作を行う。シナリオ選定の経緯は[ADR 0001](adr/0001-scenario-fraud-detection-with-agent-assist.md)を参照。

## 背景（なぜサイドカーへ移すか）

gekko_05は「各サービスのアプリケーション本体でToken Exchangeを実装する」ことをあえて選択し（[gekko_05 ADR 0002]）、RFC 8693の意味論を学習目的でコードとして直接見せた。その結果、Java/Go/Rust/Pythonそれぞれで同じRFC 8693クライアントロジックを重複実装することになった。

サイドカー方式の価値は「サービスの実装言語に関係なく、この重複を1箇所に集約できる」点にある。言語がバラバラな構成でこそこの価値が際立つため、今回もサービスは複数言語で実装する方針とする（[ADR 0002](adr/0002-token-exchange-in-envoy-sidecar.md)）。

## 背景（なぜAIエージェントの実行権限を制限するか）

AIエージェントに実行系の操作まで許してしまうと、エージェントの誤判断がそのまま不可逆な業務結果（今回は口座凍結）に直結する。これを防ぐため、以下を要件とする。

- エージェントが取得できるトークンには、読み取り・提案に必要なスコープのみを持たせ、実行系のスコープ（`account:freeze`）を含めない
- この制限はアプリケーションロジックの分岐（`if`文）ではなく、**Keycloakのスコープ設計そのもの**で強制する。エージェント側のコードにバグがあっても、そもそも実行系のトークンを取得できない構造にする
- 実行系の操作は、人間がUI上で行う明示的な操作（決定論的操作）でのみ到達可能なパスに限定する

具体的なスコープ設計は[architecture.md](architecture.md) §4、認可のディシジョンテーブルは[permission-matrix.md](permission-matrix.md)を参照。

## 委任チェーンの事後監査

「AIが何を根拠に何を提案したか」と「人間がいつ・どのトークンで確定したか」を事後に区別して追跡できることを要件とする。gekko_05の`(jti, audience)`突合方式に加え、提案と確定を結びつける`proposal_id`を新たに要件化する（詳細は[architecture.md](architecture.md) §7）。

## 業務ロジックのリアリティ水準

gekko_05と同じく「ある程度リアル」な実装とする。口座の地域・ティア（`standard`/`high-value`）とアナリストの担当地域・権限レベル（`junior`/`senior`）による2軸のアクセス制御を持たせ、ダミーレスポンスでは示せない「スコープを絞り込んで委任した先で、実際に意味のある権限チェックが行われているか」を実演する（[permission-matrix.md](permission-matrix.md) 表5）。

## gekko_05との違い

| 観点 | gekko_05 | gekko_07 |
|---|---|---|
| ドメイン | 受発注システム | 金融の不正検知・口座凍結 |
| Token Exchangeの実装場所 | アプリ層 | Envoyサイドカー（ext_authz） |
| 実行基盤 | Docker Compose | k3d（Kubernetes） |
| AIエージェント | なし | あり（読み取り・提案のみ、実行不可） |
| コード資産の再利用 | - | なし（新規実装。ドメイン・コードともに独立） |
