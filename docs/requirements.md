# 要件

本ドキュメントは「何を・なぜ実現するか」（目的・動機・要求水準、誰が何をできて何をできてはいけないかという業務要件を含む）を記録する。「誰のどんな課題を解決し、誰にどんな利益を提供するか」という一枚の全体像は[prfaq.md](prfaq.md)を参照。「どう構築したか」（現在のアーキテクチャ・認可のディシジョンテーブル・実行時シナリオ）は[architecture.md](architecture.md)、個々の設計判断の根拠・選択経緯は[docs/adr/](adr/)、各サービスの存在意義・業務ルールは[services.md](services.md)を参照。

## 目的

OAuth 2.0 Token Exchange (RFC 8693) を、マイクロサービス化された業務システムとAIエージェントが連携するローカル実行可能なサンプルで示す。特に以下2点を実演する。

1. **Token Exchangeの実装をアプリケーション本体からEnvoyサイドカー（ext_authz）へ切り出す**。サービスの実装言語やフレームワークに依存しない横断的関心事として1箇所に集約できることを、複数言語で実装されたサービス群を通じて示す（言語構成は[ADR 0007](adr/0007-per-service-language-selection.md)で選定済み）
2. **マイクロサービス群にAIエージェントを組み込む**。エージェントの権限をKeycloakのスコープ設計で厳格に制限し（読み取り・提案のみ、実行不可）、最終判断は人間の決定論的な操作でのみ確定させる設計を示す

想定ユースケース：金融の不正検知・口座凍結解除。取引パターンから自動検知エンジン（fraud-detection-engine）が口座を自動的に凍結し、AIエージェントが凍結の妥当性を分析して解除を提案、アナリストが確認の上で解除の確定操作を行う。シナリオ選定の経緯は[ADR 0001](adr/0001-scenario-fraud-detection-with-agent-assist.md)・[ADR 0011](adr/0011-scenario-ai-assisted-unfreeze.md)を参照。

## 背景（なぜサイドカーへ切り出すか）

Token Exchangeをアプリケーション本体に実装すると、サービスの実装言語ごとに同じRFC 8693クライアントロジック（トークンエンドポイントへの`grant_type=urn:ietf:params:oauth:grant-type:token-exchange`呼び出し、レスポンス解釈、エラーハンドリング）を重複実装することになる。

これをEnvoyサイドカーの`ext_authz`フィルタから呼ばれる外部サービスとして1箇所に集約すれば、アプリケーション本体は次ホップの呼び出し先を叩くだけでよくなり、実装言語に関係なくこの重複が解消される。この価値は言語がバラバラな構成でこそ際立つため、サービスは複数言語で実装する方針とする（実装方式の詳細は[ADR 0002](adr/0002-token-exchange-in-envoy-sidecar.md)）。

## 背景（なぜAIエージェントの実行権限を制限するか）

AIエージェントに実行系の操作まで許してしまうと、エージェントの誤判断がそのまま不可逆な業務結果（今回は口座凍結の解除）に直結する。これを防ぐため、以下を要件とする。

- エージェントが取得できるトークンには、読み取り・提案に必要なスコープのみを持たせ、実行系のスコープ（`account:unfreeze`）を含めない
- この制限はアプリケーションロジックの分岐（`if`文）ではなく、**Keycloakのスコープ設計そのもの**で強制する。エージェント側のコードにバグがあっても、そもそも実行系のトークンを取得できない構造にする
- 実行系の操作は、人間がUI上で行う明示的な操作（決定論的操作）でのみ到達可能なパスに限定する

上記を含む「誰が何をできて何をできてはいけないか」の具体的な業務要件は次節（BR0〜BR8）に列挙する。それを実現する具体的なスコープ設計・認可のディシジョンテーブルは[architecture.md](architecture.md) §4・§6を参照。

## 委任チェーンの事後監査

「AIが何を根拠に何を提案したか」と「人間がいつ・どのトークンで確定したか」を事後に区別して追跡できることを要件とする（BR8）。監査ログ集約基盤（[ADR 0025](adr/0025-audit-log-aggregation.md)）で、Keycloakのログインセッションid（`sessionId`）を委任チェーン1インスタンスの相関キーとし、`sub`/`jti`（発行識別子）を組み合わせて事後に再構成する（詳細は[architecture.md](architecture.md) §9）。AIの提案と人間の確定を紐付ける`proposal_id`のaccount-service側実装は、account-serviceの本実装まで持ち越している。

## 業務ロジックのリアリティ水準

「ある程度リアル」な実装とする。ダミーレスポンスではなく、実在感のあるドメインモデルと業務ルールを持たせる。口座の地域・ティア（`standard`/`high-value`）とアナリストの担当地域・権限レベル（`junior`/`senior`）による2軸のアクセス制御を持たせ、「スコープを絞り込んで委任した先で、実際に意味のある権限チェックが行われているか」を実演する（[architecture.md](architecture.md) 表5）。ダミーレスポンスではこれを示せないため、この要求水準自体が目的（AIエージェントの権限制限を実演すること）に直結する。

## 業務要件（アクセス制御）

「誰が何をできなければならないか」「誰が何をできてはいけないか」を、Keycloak・スコープ・トークンといった実装手段に一切触れない**業務要件**として定義する。[architecture.md](architecture.md) §6の各表は、ここで定めた要件番号（BR0, BR1, ...）に対応付けて検証できるようにする。

### 登場する主体

| 主体 | 説明 |
|---|---|
| junior アナリスト | 不正検知業務の担当者。担当地域が割り当てられている |
| senior アナリスト | 同上。juniorより広い範囲を扱える権限を持つ |
| AIエージェント | アナリストの依頼を受けて凍結済み口座の状況を分析し、凍結解除を提案する。人間の代理として動くが、それ自体は人間ではない |
| 自動凍結処理 | 取引パターンを監視し、疑わしい口座を自動的に凍結する業務処理。特定のアナリストの代理ではなく、システムそのものとして動く |

### 対象となるデータ・操作

| データ・操作 | 説明 |
|---|---|
| 口座の取引情報 | 各口座は地域（`region`）とティア（`standard`／`high-value`）を持つ |
| 凍結の実行 | 疑わしい取引パターンを検知した口座を自動的に凍結する操作。業務属性チェックの対象外（BR7） |
| 凍結解除の提案 | 凍結済み口座を解除すべきという提案を記録する操作。それ自体は口座に何の効果も及ぼさない（可逆・低リスク） |
| 凍結解除の実行 | 口座の凍結を実際に解除する操作（不可逆・高リスク） |

### 業務要件

**BR0（認証の必須化）**：本システムのいかなる操作も、認証された主体によってのみ実行されてよい。未認証・身元を検証できないリクエストは、要求された操作の内容に関わらず拒否されなければならない。ここでいう「認証された主体」とは、ログイン済みのアナリスト本人、そのアナリストの委任を受けたAIエージェント、または機械間認証を済ませた自動凍結処理のいずれかを指す。BR1以降の各要件は、この前提（主体の身元が確定していること）の上に成り立つ。

**BR1（担当地域の原則）**：アナリストは、自分が担当する地域の口座の取引情報のみを閲覧できる。担当地域外の口座の取引情報は一切閲覧できてはならない。

**BR2（juniorの制限）**：junior権限のアナリストは、担当地域内であってもhigh-value口座の取引情報を閲覧できてはならず、凍結解除もできてはならない。

**BR3（seniorの権限）**：senior権限のアナリストは、担当地域内であればstandard・high-value問わず取引情報を閲覧でき、凍結解除もできる。

**BR4（AIエージェントの閲覧範囲の上限）**：AIエージェントがあるアナリストの依頼を受けて取得できる取引情報の範囲は、そのアナリスト本人がBR1〜BR3に基づいて閲覧できる範囲を**超えてはならない**。AIエージェントを経由することで、本人が見られない情報が見られるようになってはならない。

**BR5（AIエージェントは実行できない）**：AIエージェントは口座凍結の解除を提案（記録）できるが、凍結解除を実行する手段を一切持ってはならない。これはアナリストの権限レベルや担当地域に関わらず、常に成り立たなければならない。

**BR6（人間の確定操作の必須化）**：口座凍結の解除の実行は、その口座に対して権限を持つアナリスト本人が、明示的な確定操作（UI上のボタン操作等、AIエージェントの応答とは別の行為）を行った場合に限り実行されてよい。AIエージェントの提案が自動的に実行に繋がってはならない。

**BR7（自動凍結処理の独立性）**：口座の自動凍結処理は、不正検知・凍結解除に関するアナリストの権限体系（担当地域・権限レベル）の影響を受けずに実行されてよい。この処理はアナリストの代理として動くものではなく、アナリストの持つ制約（BR1〜BR3）を適用する対象ではない。

**BR8（事後追跡可能性）**：口座凍結の解除が実行された場合、その実行が事前のAIエージェントの提案に基づくものであれば、どの提案に基づく実行かを事後に特定できなければならない。また、誰（どのアナリスト）が実行したかを事後に特定できなければならない。

### 誰が何をできる／できないか（早見表）

| 操作 | できる主体 | できない主体 |
|---|---|---|
| いかなる操作も | 認証済みの主体（アナリスト本人、その委任を受けたAIエージェント、認証済みの自動凍結処理）（BR0） | 未認証・身元を検証できない主体（BR0） |
| 担当地域内のstandard口座の取引照会 | junior/senior アナリスト本人。当該アナリストの依頼を受けたAIエージェント（BR4） | 担当地域が異なるアナリスト |
| 担当地域内のhigh-value口座の取引照会 | senior アナリスト本人。当該seniorの依頼を受けたAIエージェント（BR4） | junior アナリスト（BR2）。担当地域が異なるアナリスト（BR1） |
| 口座の自動凍結 | 自動凍結処理（BR7） | アナリスト・AIエージェント（この操作の主体ではない） |
| 凍結解除の提案（記録のみ） | AIエージェント（アナリストの依頼のもとで） | — （提案自体は低リスクなため主体を制限する要件はない） |
| 凍結解除の実行 | 権限のあるアナリスト本人による明示的な確定操作のみ（BR6） | AIエージェント（いかなる場合も。BR5） |
