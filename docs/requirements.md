# 要件

本ドキュメントは「何を・なぜ実現するか」（目的・動機・要求水準）を記録する。「どう構築したか」（現在のアーキテクチャ）は[architecture.md](architecture.md)、誰が何をできて何をできてはいけないかという業務要件は[access-control-requirements.md](access-control-requirements.md)、個々の設計判断の根拠・選択経緯は[docs/adr/](adr/)、具体的な業務シナリオは[use-cases.md](use-cases.md)、各サービスの存在意義・業務ルールは[services.md](services.md)を参照。

## 目的

OAuth 2.0 Token Exchange (RFC 8693) を、マイクロサービス化された業務システムとAIエージェントが連携するローカル実行可能なサンプルで示す。特に以下2点を実演する。

1. **Token Exchangeの実装をアプリケーション本体からEnvoyサイドカー（ext_authz）へ切り出す**。サービスの実装言語やフレームワークに依存しない横断的関心事として1箇所に集約できることを、複数言語で実装されたサービス群を通じて示す（言語構成は未定。[backlog.md](backlog.md)参照）
2. **マイクロサービス群にAIエージェントを組み込む**。エージェントの権限をKeycloakのスコープ設計で厳格に制限し（読み取り・提案のみ、実行不可）、最終判断は人間の決定論的な操作でのみ確定させる設計を示す

想定ユースケース：金融の不正検知・口座凍結。AIエージェントが取引パターンから凍結を提案し、アナリストが確認の上で確定操作を行う。シナリオ選定の経緯は[ADR 0001](adr/0001-scenario-fraud-detection-with-agent-assist.md)を参照。

## 背景（なぜサイドカーへ切り出すか）

Token Exchangeをアプリケーション本体に実装すると、サービスの実装言語ごとに同じRFC 8693クライアントロジック（トークンエンドポイントへの`grant_type=urn:ietf:params:oauth:grant-type:token-exchange`呼び出し、レスポンス解釈、エラーハンドリング）を重複実装することになる。

これをEnvoyサイドカーの`ext_authz`フィルタから呼ばれる外部サービスとして1箇所に集約すれば、アプリケーション本体は次ホップの呼び出し先を叩くだけでよくなり、実装言語に関係なくこの重複が解消される。この価値は言語がバラバラな構成でこそ際立つため、サービスは複数言語で実装する方針とする（実装方式の詳細は[ADR 0002](adr/0002-token-exchange-in-envoy-sidecar.md)）。

## 背景（なぜAIエージェントの実行権限を制限するか）

AIエージェントに実行系の操作まで許してしまうと、エージェントの誤判断がそのまま不可逆な業務結果（今回は口座凍結）に直結する。これを防ぐため、以下を要件とする。

- エージェントが取得できるトークンには、読み取り・提案に必要なスコープのみを持たせ、実行系のスコープ（`account:freeze`）を含めない
- この制限はアプリケーションロジックの分岐（`if`文）ではなく、**Keycloakのスコープ設計そのもの**で強制する。エージェント側のコードにバグがあっても、そもそも実行系のトークンを取得できない構造にする
- 実行系の操作は、人間がUI上で行う明示的な操作（決定論的操作）でのみ到達可能なパスに限定する

上記を含む「誰が何をできて何をできてはいけないか」の具体的な業務要件は[access-control-requirements.md](access-control-requirements.md)（BR0〜BR8）に列挙する。それを実現する具体的なスコープ設計は[architecture.md](architecture.md) §4、業務要件との対応関係を含む認可のディシジョンテーブルは[access-control-design.md](access-control-design.md)を参照。

## 委任チェーンの事後監査

「AIが何を根拠に何を提案したか」と「人間がいつ・どのトークンで確定したか」を事後に区別して追跡できることを要件とする（[access-control-requirements.md](access-control-requirements.md) BR8）。トークンの`jti`（発行識別子）と`audience`の組を突合キーとする方式に加え、AIの提案と人間の確定を紐付ける`proposal_id`を導入する（詳細は[architecture.md](architecture.md) §8）。

## 業務ロジックのリアリティ水準

「ある程度リアル」な実装とする。ダミーレスポンスではなく、実在感のあるドメインモデルと業務ルールを持たせる。口座の地域・ティア（`standard`/`high-value`）とアナリストの担当地域・権限レベル（`junior`/`senior`）による2軸のアクセス制御を持たせ、「スコープを絞り込んで委任した先で、実際に意味のある権限チェックが行われているか」を実演する（[access-control-design.md](access-control-design.md) 表5）。ダミーレスポンスではこれを示せないため、この要求水準自体が目的（AIエージェントの権限制限を実演すること）に直結する。
