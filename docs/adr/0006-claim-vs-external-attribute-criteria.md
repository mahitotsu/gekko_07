# ADR 0006: トークンのクレームにするか業務データとして外部化するかの判断基準

- **Status**: Accepted
- **Date**: 2026-09-13

## Context

[architecture.md](../architecture.md)の「認証（アナリストのログイントークン）」で、アナリストの担当地域・権限レベルをログイントークンのクレームに埋め込まず、analyst-attribute-serviceが保持する外部の業務データとして都度照会する設計にした。この判断は今回限りの個別事情ではなく、「あるデータをトークンのクレームにすべきか、業務サービス側に外部化して都度照会すべきか」という繰り返し登場しうる一般的な設計判断の一事例である。今後同種の判断が必要になった際に一貫した基準を持てるよう、判断基準そのものをここに記録する。

## Decision

判断は**2段階のANDゲート**として捉える。両ゲートは答えている問いが異なる独立した軸であり、両方を通過して初めてアクセスが許可される。

- **第一ゲート：scope（委譲の天井）** — 「このトークン（＝このクライアント・この同意）は、そもそも原理的にどの操作カテゴリを行使してよいか」を表す、クライアント/同意単位の粗い上限。`account:read`/`account:propose`/`account:freeze`/`account:unfreeze`がこれに当たる（[architecture.md](../architecture.md) §4）
- **第二ゲート：業務属性による実行時判断（RBAC/ABAC）** — 「今この特定のアナリストは、この特定の口座に対して何ができるか」を表す、ユーザー・リソース単位の細かい実行時判断。担当地域・権限レベルがこれに当たる（[architecture.md](../architecture.md) 表5）

本システムは既にこの2ゲートを実装している。frontendのトークンは`account:unfreeze`という天井を持つが、そのトークンでjuniorアナリストがhigh-value口座の凍結解除をしようとすると第二ゲート（表5）で拒否される。逆にfraud-mcp-serverは`account:read`という天井しか持たないため、どのアナリストの代理として動いていようと、凍結解除という操作カテゴリ自体にそもそも到達できない（表1・表2）。

この2つのゲートが答えている問いの違いから、あるデータをどちらの層に置くべきかの判断基準が導かれる。以下の3つの軸で判断し、**いずれか1つでも「外部化すべき」側に該当すれば、クレームに埋め込まず業務サービス側への生の照会に委ねる。**

1. **役割（最も本質的な軸）**：このデータは「原理的に何ができるか」という委譲の天井を表すか、それとも「今この特定の主体が何をできるか」という実行時の個別業務判断を表すか。
   - 委譲の天井（scope）はクライアント・同意単位で固定され、Token Exchangeは狭める方向にしか働かない（[ADR 0005](0005-single-audience-tokens-only.md)）。トークン発行時に確定し寿命中は変わらないことがむしろ望ましい性質であり、クレームに向く
   - 実行時の個別業務判断（担当地域・権限レベル等）は「今」を問う性質上、判断のたびに評価し直す必要がある。これをクレームとして固定してしまうと、天井と実行時判断という異なる階層が1つに潰れてしまい、本来ANDであるべき2つのゲートが実質1つになる。担当地域・権限レベルの変更（異動、緊急の権限剥奪等）が、判断のたびに評価されるべき実行時の事実である以上、外部化が自然な帰結になる
2. **オーナーシップ**：このデータの正典（source of truth）はAS（Keycloak）自身か、それとも特定の業務ドメイン/サービスか。
   - 委譲の天井（scope）はAS自身が管理するOAuthの同意・権限割当そのものであり、ASが自然な正典
   - 実行時の個別業務判断のもとになるデータ（担当地域等）は、HR・業務システム等、他のシステムが正典である場合が多い。ASにも複製すると、複製元の変更がASへ反映されるまでの間、両者が食い違うリスクを常に抱える
3. **機密性**：このデータを、トークンを保持しうる全ての当事者（発行元、中継するサービス、各ホップのアクセスログ・分散トレーシング基盤）が知ってよいか。
   - JWTは署名されているだけで暗号化されていない。`aud`によるaudience制限は「このリソースサーバーが受理すべきか」という検証時の受理条件であって、意図した宛先以外に内容を隠す機密性は提供しない
   - 委譲の天井（scope）はそのトークンを要求した当事者自身が交渉して得た結果であり、隠すべき相手が存在しない。一方、実行時の個別業務判断のもとになるデータは、そのデータを必要とする特定のサービス（account-service）以外の中継者（fraud-mcp-server等）には見せる理由がなく、トークンという複数ホップを転々とする媒体に乗せるべきではない

## この基準をscope自体に適用した場合

scopeは定義上「委譲の天井」そのものなので、軸1（役割）に照らせば自明にクレーム側である。軸2（オーナーシップ）・軸3（機密性）も無条件にクレーム側を支持する（Decisionの各項目参照）。したがって、scopeをトークンに含める設計と、担当地域・権限レベルを外部化する設計は、同じ基準の異なる帰結であり矛盾しない。

なお、委譲の天井が寿命中不変であってよい性質だとしても、トークン自体が漏洩・誤用された場合の被害範囲を抑えるため、交換後トークンのアクセストークン有効期間は短く設定する（[architecture.md](../architecture.md)参照）。これは軸1〜3のいずれの結論も変えないが、多層防御として別途行う運用上の配慮である。

## 実装レイヤーへの帰結

軸1（役割）の違いは、実装上どこで判定できるかの違いにも直結する。

- **委譲の天井（scope）の判定**：トークン単体の中身だけで完結するため、**アプリケーション（account-service）のコードに到達する前**、Envoyサイドカーの境界（`envoy.filters.http.jwt_authn`＋`envoy.filters.http.rbac`等）で完結できる。どの具体的な口座にアクセスしようとしているかを一切知らなくても判定できるため、汎用的なインフラ層に任せられる
- **実行時の個別業務判断（表5）の判定**：「どの口座か」「その口座のregion/tierは何か」というリクエスト固有の情報と、呼び出し元の属性を突き合わせる必要があるため、**account-serviceのアプリケーションコードに入ってから**でなければ判定できない。これをサイドカー側に持たせようとすると、サイドカー自身がaccount-serviceの業務知識（口座の属性モデル）を持つ羽目になり、[ADR 0002](0002-token-exchange-in-envoy-sidecar.md)が目指す「アプリとインフラの責務分離」が崩れる

### ルール（MUST）：scopeチェックの実施箇所を1点に固定する

**本システムでは、scopeによるアクセス制御は、Envoyサイドカーの受信側（アプリの外）で行うか、やむを得ずアプリ内で行う場合もリクエストの入口（ハンドラの先頭、表5等のABAC判定より前）でのみ行う。ビジネスロジックの途中や、ABAC判定の後にscopeチェックを行ってはならない。**

理由は3つある。

1. **2ゲートモデルの独立性を保つため**：scopeチェックがABAC判定と混在すると、「委譲の天井」と「実行時判断」という別の問いに答えるロジックが1箇所に絡み合い、2つのゲートが本当に独立して機能しているかを検証できなくなる
2. **監査可能性**：scopeチェックの実施箇所が1点（サイドカー設定、またはハンドラの先頭）に定まっていれば、「AIエージェントに凍結解除権限が無いことがどう保証されているか」を、業務ロジック全体を読まずに確認できる
3. **check-then-use事故の防止**：scope不足のリクエストに対して、途中まで（副作用のある）ビジネスロジックが実行されてしまう経路を作らない。scopeチェックが入口を通過して初めて後続のコードが動く、という順序を構造的に保証する

これは[ADR 0002](0002-token-exchange-in-envoy-sidecar.md)（Token Exchangeをサイドカーへ寄せ、アプリの負担を最小化する）とも一貫する方向性を示す：scope検証はEnvoyサイドカーの受信側（ingress）に寄せられる余地があるが、表5のABAC判定はaccount-serviceのアプリ内に残さざるを得ない。前者をサイドカー側に実装するかどうかは未実装・未決定（[architecture.md](../architecture.md)参照）。

## Consequences

- この基準に照らすと、analyst-attribute-serviceの設計（担当地域・権限レベルの外部化）は3軸全てで「外部化すべき」側に該当する：これらは実行時の個別業務判断のもとになるデータであり、正典は業務ドメイン（人事上の配属情報）であり、fraud-mcp-server等の中継者には見せる必要がない
- 逆に、3軸のいずれにも該当しない安定的・非機密的なデータ（例：`sub`、表示言語設定のような認証イベント自体の事実）は、クレームとして埋め込んで構わない
- 今後、新しいデータ項目についてクレームか外部化かを検討する際は、まず軸1（委譲の天井か実行時の個別業務判断か）で大枠を判断し、軸2・3で裏付けを取る、という順序で機械的に当てはめる
- 参考にした考え方：NIST SP 800-162（ABAC、属性の発行源=PIPを認可ロジック=PDPから分離するモデル）は軸1・軸2を、NIST SP 800-207（ゼロトラストアーキテクチャ、継続的な認可評価）は軸1の「実行時判断は都度評価すべき」という部分を、それぞれ裏付ける考え方として参照できる
