# ADR 0006: トークンのクレームにするか業務データとして外部化するかの判断基準

- **Status**: Accepted
- **Date**: 2026-09-13

## Context

[access-control-design.md](../access-control-design.md)の「認証（アナリストのログイントークン）」で、アナリストの担当地域・権限レベルをログイントークンのクレームに埋め込まず、analyst-attribute-serviceが保持する外部の業務データとして都度照会する設計にした。この判断は今回限りの個別事情ではなく、「あるデータをトークンのクレームにすべきか、業務サービス側に外部化して都度照会すべきか」という繰り返し登場しうる一般的な設計判断の一事例である。今後同種の判断が必要になった際に一貫した基準を持てるよう、判断基準そのものをここに記録する。

## Decision

以下の3つの軸で判断する。**いずれか1つでも「外部化すべき」側に該当すれば、クレームに埋め込まず業務サービス側への生の照会に委ねる。**

1. **オーナーシップ**：このデータの正典（source of truth）はAS（Keycloak）自身か、それとも特定の業務ドメイン/サービスか。
   - 認証イベント自体に関する事実（`sub`、認証方式、発行時刻等）はASが自然な正典であり、クレームに向く
   - HR・業務システム等、他のシステムが正典であるデータをASにも複製すると、複製元の変更がASへ反映されるまでの間、両者が食い違うリスクを常に抱える。複製自体を作らないことがこのリスクへの根本対応になる
2. **機密性**：このデータを、トークンを保持しうる全ての当事者（発行元、中継するサービス、各ホップのアクセスログ・分散トレーシング基盤）が知ってよいか。
   - JWTは署名されているだけで暗号化されていない。`aud`によるaudience制限は「このリソースサーバーが受理すべきか」という検証時の受理条件であって、意図した宛先以外に内容を隠す機密性は提供しない
   - 特定のサービスだけが知るべきデータを「audienceを絞ったクレーム」として設計しても、トークンを手にした全員が中身を読める。真に機密性を保ちたいデータは、そのデータを必要とするサービスへの直接照会に留め、複数ホップを転々とする「トークン」という媒体には乗せない
3. **鮮度要件（volatility）**：このデータに基づく判断が、常に最新の実態を反映する必要があるか、それとも一定期間古くても許容できるか。
   - 現実には、業務データへの生の照会であっても、性能上の理由から結果がキャッシュされる可能性が高い（[backlog.md](../backlog.md)の「Token Exchange結果のキャッシュ」参照）。したがって「クレームは陳腐化するが外部照会なら常に無条件で最新」という単純な二分法は正確ではない。キャッシュを考慮すると、どちらの方式でも何らかの陳腐化の窓は生じうる
   - 本当に問うべきなのは「その陳腐化の窓の大きさを、誰が・何の目的で決めているか」である。クレームに埋め込む場合、陳腐化の窓は**そのトークン自身のアクセストークン有効期間（Access Token Lifespan）**に引きずられる。これはログイントークンに限った話ではない——交換後に発行されるトークンにも固有の有効期間があり、明示的に短く設定しない限り、クライアントはその交換後トークンを有効期間中は繰り返し使い回せる。つまり「クレームをどのトークンに埋め込むか」に関わらず、そのトークンの有効期間設定が認可の鮮度のためにチューニングされたものでなければ、同じ問題が生じる
   - 対して、外部照会の結果をキャッシュする場合、そのキャッシュTTLは**性能とのトレードオフのために個別に意図して選ぶ値**（秒〜数十秒規模を想定）にできる。認可の鮮度が重要なデータほど、この「窓の大きさを目的に応じて明示的に制御できるか」という違いが効いてくる

## この基準をscope自体に適用した場合

本システムは`account:read`・`account:freeze`等のscopeをトークンのクレーム（`scope`）として直接使っている。これは一見、外部化の基準と緊張関係にあるように見えるため、念のため同じ3軸で検証する。

1. **オーナーシップ**：どのクライアントにどのscopeを許可するかは、Keycloakのoptional client scope割当そのものであり、**AS自身が正典**である。担当地域のように業務ドメイン側に別の正典が存在するデータとは異なる
2. **機密性**：scope名は「このトークンで何ができるか」という、そのトークンを要求した当事者自身が交渉して得た結果である。担当地域のように「たまたま無関係な業務データが同乗している」のとは性質が異なり、隠すべき相手が存在しない（要求者は自分が何を要求したかを既に知っている）
3. **鮮度要件**：交換によって発行されるトークンにも、ログイントークンと同様に固有のアクセストークン有効期間がある。これを明示的に短く設定しない限り、クライアント（fraud-mcp-server等）はその交換後トークンを有効期間中は繰り返し使い回せるため、「交換の都度Keycloakがscopeを再評価する」とは限らない——アプリ層に明示的なキャッシュを追加しなくても、トークン自体の有効期間だけで同様のことが起こりうる。加えてアプリ層のToken Exchange結果キャッシュ（backlog.md参照）が入れば、その分の窓も上乗せされる。したがって、scopeについても「陳腐化の窓の大きさを認可の鮮度を意識して意図的に短く設定しているか」が問われる点は担当地域と同じであり、**scopeが無条件に安全というわけではない**。本システムでは交換後トークンの有効期間を短く設定する方針とする（具体的な秒数は実装時に決定。[backlog.md](../backlog.md)参照）

オーナーシップ・機密性の2軸は無条件にクレーム側を支持する。鮮度要件は、交換後トークンの有効期間を短く設定するという運用判断があって初めて成り立つ条件付きの支持であり、他の2軸のような構造的な保証ではない。それでも2軸が無条件に支持している以上、scopeをトークンに含める設計と、担当地域・権限レベルを外部化する設計は一貫しており矛盾しない。

## Consequences

- この基準に照らすと、analyst-attribute-serviceの設計（担当地域・権限レベルの外部化）は3軸全てで「外部化すべき」側に該当する：正典は業務ドメイン（人事上の配属情報）であり、fraud-mcp-server等の中継者には見せる必要がなく、権限剥奪は即時に反映される必要がある。3軸のいずれか1つで十分な根拠になるが、今回は3つとも同じ結論を支持しており、一貫した設計であることを裏付ける
- 逆に、3軸のいずれにも該当しない安定的・非機密的なデータ（例：`sub`、表示言語設定のような認証イベント自体の事実）は、クレームとして埋め込んで構わない
- 今後、新しいデータ項目についてクレームか外部化かを検討する際は、この3軸を機械的に当てはめて判断する
- 参考にした考え方：NIST SP 800-207（ゼロトラストアーキテクチャ、継続的な認可評価）は鮮度要件の軸を、NIST SP 800-162（ABAC、属性の発行源=PIPを認可ロジック=PDPから分離するモデル）はオーナーシップ・機密性の軸を、それぞれ裏付ける考え方として参照できる
