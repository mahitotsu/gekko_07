# ADR 0009: Envoy ingress側の責務範囲とバイパス防止

- **Status**: Accepted
- **Date**: 2026-09-14

## Context

[ADR 0002](0002-token-exchange-in-envoy-sidecar.md)はEnvoyサイドカーの**egress側**（次ホップへのToken Exchange）の実装方式を決めたが、**ingress側**（自分宛てのリクエストを受けた時に何を検証するか）の責務範囲は未決定だった（[architecture.md](../architecture.md)「scope検証をサイドカー側（受信側）に寄せるか」）。

各サービスの実装が始まる前に、次の2点を決める必要がある。

1. Envoyのingress側に何を任せ、どこからアプリに残すか
2. アプリが「Envoyを経由した前提」で実装される以上、Envoyを経由しないトラフィックが直接アプリに届いてしまった場合の被害は致命的になる。これをどう防ぐか

## Decision

### 1. Envoy（ingress側）の責務範囲

[ADR 0006](0006-claim-vs-external-attribute-criteria.md)の2ゲートモデルをそのまま責務分界点として使う。

**Envoyに任せる（トークン単体で完結し、業務データに依存しない処理）**：

- **JWT検証**（`jwt_authn`フィルタ）：署名（KeycloakのJWKS）、`iss`、`exp`、そして`aud`がこのサービス自身であることの検証（[ADR 0005](0005-single-audience-tokens-only.md)の機械的強制）
- **スコープ/RBACチェック**（`rbac`フィルタ）：[architecture.md](../architecture.md)表2（パス・メソッドと必要スコープの対応）をポリシーとして持たせる。ADR 0006の「第一ゲート（委譲の天井）」
- **検証済みの身元をヘッダーでアプリへ転送**（`x-auth-sub`, `x-auth-scope`, `x-auth-jti`等）。アプリは自前のJWTライブラリを持たない

**アプリに残す**：[architecture.md](../architecture.md)表5のようなABAC判定（口座の`region`/`tier`とアナリストの担当地域・権限レベルの突合）。業務データに依存するためEnvoyには原理的にできない（ADR 0006の「第二ゲート」）。

これにより、ADR 0002が扱っていたegress側のToken Exchangeに加え、ingress側のJWT検証・スコープ判定も「言語に依存しない横断的関心事」として同じ理由でサイドカーへ切り出す。

### 2. バイパス防止

**再整理**：呼び出し元がegress側のToken Exchangeを省略しても、それ自体は致命的ではない——受信側のingress Envoyが`aud`不一致やスコープ不足で弾く。本当に守るべき一点は「**受信側の検証そのものが素通りされること**」、すなわちリクエストが自サービスのEnvoyを経由せずアプリコンテナへ直接届くケースである。これは運用上の注意で防ぐのではなく、構造的に不可能にする。

3層で防御する。

**① 主対策（構造的・必須）**：アプリは`127.0.0.1:<port>`にのみbindする。KubernetesのServiceはアプリのポートではなくEnvoyのリスナーだけを指す。サイドカーは同一Podのネットワーク名前空間を共有するため、これだけでPod外からの直接到達は原理的に不可能になる。ポリシーやコードレビューに依存しない、トポロジーによる保証。

**② 多層防御（安価）**：アプリ自身も「接続元がloopbackでなければ拒否」を実装する。①の設定が将来事故で崩れても（例：bindアドレスの誤変更）、独立した第二の壁になる。

**③ 多層防御（Pod内合言葉によるヘッダーの真正性検証）**：①②はいずれも「Pod内から来たか」しか見ておらず、Envoyの設定ミス（jwt_authn/rbacを通らない別経路からアプリへ転送してしまう）やデバッグ用ephemeral containerからの誤操作までは防げない。そこで、Envoyが付与する`x-auth-*`系ヘッダーが「本物の検証チェーンを実際に通過した結果か」をアプリ側で検証可能にする。

- Podに軽量なinitContainer（例：`openssl rand -hex 32 > /handshake/token`）を追加し、`emptyDir`ボリュームでinitContainer・app・Envoyの3者に共有する。initContainerはメインコンテナ起動前に完了することがKubernetesにより保証されるため、レースコンディションなく「先に生成、後で両方が読む」が書ける
- この値はK8s SecretではなくemptyDir上のファイルであり、Pod専用でPodが消えれば消える。`kubectl get secrets`にも現れず、サービス単位ではなくPodごとに別の値になる（1つのreplicaが侵害されても他のreplicaには影響しない）。この構成は、クラウドメタデータサーバーをSSRFから守るサイドカー等で実際に使われている確立されたパターンである
- Envoy側は、jwt_authn・rbacフィルタを**通過した後**にのみこのファイルの値をヘッダーとして付与する（フィルタチェーンの手前で付けると素通りしたリクエストにも付いてしまい意味がなくなる）。具体的な付与方式（Luaフィルタでのファイル読み込みが有力候補）は[ADR 0002](0002-token-exchange-in-envoy-sidecar.md)が予定する「1ホップ先行検証」のタイミングで実機確認する
- アプリは、この合言葉ヘッダーが正しいことを検証してから初めて他の認証ヘッダー（`x-auth-sub`等）を信用する。合言葉が無い・不一致の場合と、認証ヘッダーが欠落・不正な場合は、どちらも同じ「fail close」として扱う

**検討したが見送る対策**：mTLS・NetworkPolicyによるゼロトラストメッシュ化（[ADR 0003](0003-k3d-without-istio.md)の方針と一貫）。トークンの署名・audience・scope検証自体が実質的な認可境界であり、①〜③で塞がれない残存リスクは限定的なため、今回のスコープでは見送る。より厳格な代替として、TCPループバックではなくUnixドメインソケット＋ファイルパーミッション（`securityContext.runAsUser`をコンテナごとに変え、ソケットmodeを絞る）でOSレベルにアクセスを制限する手法も確立されたベストプラクティスとして存在するが、appが5言語・5フレームワークそれぞれでUnixソケットのリッスンに対応するコストが、今回防ぎたい脅威（デバッグ誤操作・設定ミス）に対して過大と判断し見送る（[architecture.md](../architecture.md)に記録）。

### 3. テスト容易性：バイパススイッチを作らない

②③の検証ロジックは、k8s環境外（ローカル開発・CI上の単体/統合テスト）でも動かせる必要があるが、そのための「テスト時だけ検証を無効化するフラグ」は**絶対に作らない**。これは[CWE-489](https://cwe.mitre.org/data/definitions/489.html)（Active Debug Code：デバッグ用の迂回路が本番に紛れ込む）そのものであり、フラグの設定漏れ・誤爆で本番の認可が丸ごと無効化されるリスクを抱え込むことになる。

代わりに、**検証ロジックは環境によらず単一**とし、検証に使う**期待値の出どころだけ**を設定可能にする（dependency injection）。

- **合言葉チェック**：期待値をどこから読むか（ファイルパス。既定値はk8sのinitContainerが書くパス）を環境変数で設定可能にする。アプリのコードは常に「設定されたパスのファイルを読んで比較する」だけを行い、本番/テストで分岐しない。ローカル・CIでのテストでは、initContainerの代わりにテストハーネス自身が同じ形式のファイルを一時パスに書き込むだけでよい（どの言語でも一時ファイル作成は日常的な操作であり、特別な迂回路を要しない）
- **loopback限定チェック**：多くのin-processテストクライアント（Go の`httptest`、SpringのMockMvc、PythonのASGI TestClient等）は送信元アドレスを明示的に設定できるため、正常系テストでは`127.0.0.1`を、異常系テスト（拒否の確認）ではそれ以外を設定すればよい。実バイナリ同士の統合テストも、テストクライアントとappを同じマシンで動かす限り自然にloopbackになり、k8s固有の細工は不要
- 両者とも、この設計により「異常系（合言葉不一致・loopback外）が正しく拒否されること」自体を自動テストの対象にできる。バイパススイッチを作らないことは、むしろテストカバレッジ上のプラスになる

各サービスの実装時、このenv var名（例：`HANDSHAKE_TOKEN_FILE`）は言語をまたいで統一した命名にする。

## Consequences

- Envoyの具体的なbootstrap設定（jwt_authn/rbac/Luaフィルタの記述）は未着手。[ADR 0002](0002-token-exchange-in-envoy-sidecar.md)の「1ホップ先行検証（fraud-mcp-server→account-service）」で、egress側のToken Exchangeと同時にingress側のこの一式（JWT検証・スコープチェック・合言葉付与）も検証する
- Pod構成が「アプリ+Envoyの2コンテナ」から「initContainer 1つ+アプリ+Envoyの2コンテナ」に変わる。architecture.md §3を更新した
- 各サービスの実装時、loopback限定bind・合言葉検証・認証ヘッダー検証を「共通の最小限の起動時ロジック」として最初に書くことになる。5言語それぞれでの具体的な書き方は実装時に決める
- Unixドメインソケット化・NetworkPolicyは見送ったが、将来「同一Pod内でアプリが侵害された場合」まで守る要求が出てきたら再検討する（architecture.mdに記録）
- アプリのポートがPod外から到達不能であることの実機検証（curlで直接pod IPを叩いて拒否されることの確認等）を、ADR 0002の先行検証項目に追加する
