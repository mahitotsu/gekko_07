# 4. AI エージェントのアイデンティティと認可

> 対象読者：ここまで（[第 2 章](02-token-exchange.md)の Impersonation、[第 3 章](03-scope-and-audience-topology.md)のスコープによる封じ込め）を読んだ方。
> この章のねらい：AI エージェントに「誰の代理か」という身元をどう持たせ、その権限をどう人間の範囲内に抑え、事後にどう確かめられるようにするかを見ていきます。

## 4.1 AI エージェント特有の難しさ

AI エージェントを社内システムに組み込むとき、従来のマイクロサービスにはない難しさが 3 つ出てきます。

1. **身元の問題**：エージェントは「田中さんの依頼で動く」けれど、それ自体は田中さんではありません。かといって、完全に独立した機械でもありません。どういう身元で API を呼ぶのがよいのでしょうか
2. **権限の問題**：エージェントが誤った判断をしても、被害を業務上安全な範囲にとどめたいところです。特に、取り消せない操作はさせたくありません
3. **説明責任の問題**：エージェントは非決定的です（同じ入力でも出力が揺れます）。「なぜこの結論になったのか」「本当にそう提案したのか」を、後から人間が確かめられる形で残せるでしょうか

このサンプルでは、この 3 つに、それぞれ Token Exchange・スコープ設計・監査で向き合っています。順に見ていきます。

## 4.2 身元：「本人の代理」を Impersonation で表す

エージェントの身元の持たせ方には、大きく 2 つの選択肢があります。

- **A. エージェント自身の身元で動く**（機械間認証）：エージェントに固有のアカウントを与え、その権限で API を呼びます。ただしこれだと「田中さんの依頼か、鈴木さんの依頼か」が区別できず、田中さんが見られない口座まで、エージェントの権限で見えてしまう恐れがあります
- **B. 依頼した人間の代理として動く**（委任）：田中さんのトークンを起点に Token Exchange し、`sub` を田中さんのまま維持します

このサンプルは **B** を採っています。[第 2 章](02-token-exchange.md)の Impersonation 方式により、`sub` は委任チェーンの端まで田中さんのままです。ですから account-service が「このリクエストは誰の権限で処理すべきか」を判定するとき、対象は常に田中さん本人になります。

この結果として成り立つのが、業務要件 **BR4**「AI エージェントの閲覧範囲は、依頼したアナリスト本人が見られる範囲を超えてはならない」です（[docs/requirements.md](../docs/requirements.md)）。エージェントを経由したからといって、田中さんが直接は見られない口座が見えるようになる、ということが起きません。理由は次のとおりです。

- `sub` が田中さんのまま → account-service の口座別アクセス判定（担当地域・権限レベル）が、田中さん本人の属性に対して行われます（[docs/architecture.md](../docs/architecture.md) 表5）
- AI 経路から属性サービス（analyst-attribute-service）へ直接到達する道がない → 別人の属性を使って迂回することもできません（[第 3 章 3.5](03-scope-and-audience-topology.md#35-なぜホップ飛ばしもできないのか)、[docs/architecture.md](../docs/architecture.md) 表3）

エージェントは「田中さんという窓」を通してしか世界を見られず、その窓の大きさは田中さん本人と同じ、というイメージです。

> なお、このサンプルには「機械間認証（A）」の例もあります。取引を監視して口座を自動凍結する fraud-detection-engine は、特定のアナリストの代理ではなく**システムそのもの**として動くので、ユーザー委任チェーンには参加せず、自分の身元（client_credentials グラント）で動きます（[docs/requirements.md](../docs/requirements.md) BR7）。「人間の代理」と「独立した機械」を、身元の持たせ方で使い分けている例です。

## 4.3 権限：読み取り・提案までにとどめる

エージェントの権限を「読み取り・提案」までにとどめる仕組みは、[第 3 章](03-scope-and-audience-topology.md)で見たとおり、スコープの設計で成り立っています。エージェント経路のトークンには `account:unfreeze` が載りません（BR5）。

ここでもう一つ、シナリオの側の工夫があります。「エージェントにやらせること」を**取り消せる・低リスクな操作**に限定している点です。

- **提案（`account:propose`）**：「この口座は解除すべき」という記録を残すだけです。口座の状態は変わりません。仮に間違っていても、記録が 1 件増えるだけで、口座への実害はありません
- **実行（`account:unfreeze`）**：口座の凍結を実際に解きます。取り消せない、高リスクな操作です

エージェントには提案までしかさせず、実行は人間に残します。エージェントが誤って「解除すべき」と提案しても、それは提案が 1 件増えるだけで、口座は凍結されたままです。**エージェントの誤りが、取り消せない結果に直結しない**ようにしている、とお考えください。

## 4.4 最後の砦：人間の確定操作

では、凍結解除は誰がどう実行するのでしょうか。**その口座に権限を持つアナリスト本人が、UI 上で明示的な確定操作（ボタン操作）を行ったときだけ**です（BR6）。

- アナリストがダッシュボードで提案を見て、「承認」し、「凍結解除を確定」ボタンを押します
- そのとき初めて frontend が `account:unfreeze` トークンを Token Exchange で取得し、account-service の実行 API を呼びます
- AI の応答が自動的に実行につながることはありません。人間の操作が別途必要です

ここで「決定論的」なのは、人間の判断そのものではありません（人間の判断も、AI と同じく揺れます）。決定論的なのは、**明示的な確定操作が無ければ口座の状態が変わらない、という制御の経路**です。非決定的な AI の助言と、AI から切り離された明示的な人間の確定操作を、はっきり分けている、ということです。AI は「提案」という助言を出しますが、引き金を引くのは常に人間です。しかもその人間は、その口座を扱う権限（担当地域・権限レベル）を持っていなければなりませんし、提案を承認できるのは**その提案を依頼した本人**に限られます（BR9）。

さらにこのサンプルでは、AI の結論が「解除の根拠なし」だった場合も、人間の確認を必須にしています（BR10）。「AI が根拠なしと言ったから凍結を継続」を自動で確定させず、依頼した本人が確認して初めて確定します。**AI のどの結論も、それ単独では口座の状態を動かせない**、という設計です。

## 4.5 説明責任：非決定的な AI を、決定的に確かめる

AI は非決定的です。だからこそ「どの API が、どの権限で、いつ呼ばれたか」「その凍結解除は、どの提案に基づき、誰が確定したか」を、後から**再現でき、確かめられる**形で残す必要があります（BR8）。ここで一つ、正直にしておきたい線引きがあります。ログから確かめられるのは「**AI 経路がどのデータへのアクセスに成功したか**」までで、「モデルがそのレスポンスを内部でどう使い、どの情報が結論にどれだけ寄与したか」までは証明できません。監査で保証できるのは「アクセスと操作の追跡」であって「AI の思考の中身」ではない、という区別です。このサンプルの監査は、次の 2 段構えになっています。

### 段階①：記録して追跡できるようにする

[第 2 章](02-token-exchange.md)の Impersonation により、委任チェーン全体で `sub` は田中さんのままです。これを軸に、各ホップのトークンの `jti`（トークン固有 ID）・`scope`・`audience` をログから拾うと、「誰が・どの API を・どの権限で呼んだか」を追跡できます（[docs/architecture.md](../docs/architecture.md) §9）。

- `sub` は「誰が」を、`scope`/`jti` は「各ステップで何を」を表します
- `scope=account:read`／`account:propose` のアクセスは「AI 経路が読み取り・提案を行った」記録として、`scope=account:unfreeze` のアクセスは「人間が承認・実行を行った」記録として残ります
- 提案と、その後の承認・実行は、業務データ上の **`proposalId`** で紐づきます。「この実行は、どの提案に基づくものか」は、この `proposalId` でたどれます（BR8 の核心はここです）
- `sessionId`（Keycloak のログインセッション id）は、ログインセッション単位で全ホップをまとめる grouping です（同一セッション内の並行操作までは区別しません。同じログインの別タブは同じ値になります）。提案と実行の紐付けは `proposalId`、各操作が正当な権限で行われたかは `sub`/`scope`/`jti` が担うので、監査にはこの粒度で足ります

### 段階②：自己申告を鵜呑みにせず、第三者の記録と突き合わせる

ここは特に大事なところです。account-service は「誰が提案し・誰が承認し・誰が実行したか」を自分で記録します（自己申告）。ですが、記録した本人の申告だけを信じるのは、監査としては物足りません。そこでこのサンプルでは、**判断に一切関与しない独立したサービス（audit-service）**が、account-service の自己申告を、**認可サーバー・通信路が残した第三者の記録**（Keycloak のトークン発行ログ、account-service の Envoy アクセスログ）と突き合わせて確かめます（[ADR 0040](../docs/adr/0040-audit-service-reconciliation.md)）。

- 突き合わせの対象は、**`account:unfreeze` を要求する操作（承認・却下・凍結解除の実行）だけ**です。取り消せる・低リスクな提案の新規作成（`account:propose`）は、記録は残りますが突き合わせの対象にはしていません（[docs/architecture.md](../docs/architecture.md) §9）
- 自己申告に「この `jti` のトークンで凍結解除した」とあるなら、
  - Keycloak のイベントログに、その `jti` のトークン発行記録があるか
  - account-service の Envoy アクセスログに、その `jti` で対応する API への成功リクエストがあるか
- **両方が確認できて初めて一致**とみなします

そしてもう一つの原則があります。**この確認役（audit-service）は AI を使いません**。判定は `jti` の完全一致だけで行います。確認役自身が AI のような非決定性を持ってしまうと、「確認役は再現でき、説明できる」という監査の前提が崩れてしまうためです。**非決定的な AI の仕事を、決定的な仕組みで確かめる**——この役割分担を、AI を業務に組み込むうえでのよりどころにしています。

なお、この突き合わせの結果は全口座を横断する情報になるため、閲覧できるのは senior アナリストに限っています（BR11。[ADR 0042](../docs/adr/0042-audit-service-senior-gate.md)）。

## 4.6 この章のまとめ

AI エージェントを業務に組み込むときの 3 つの難しさに、このサンプルは次のように向き合っています。

| 難しさ | このサンプルでの向き合い方 | 対応要件 |
|---|---|---|
| 身元 | Impersonation で「本人の代理」を表し、`sub` を本人のまま維持。権限判定は常に本人に対して行う | BR4 |
| 権限 | スコープ設計で、読み取り・提案（取り消せる・低リスク）にとどめる。実行は人間の確定操作のみ | BR5・BR6・BR9・BR10 |
| 説明責任 | `sub`/`jti`/`scope` による追跡と、独立サービスによる自己申告と第三者記録の**決定的な**突き合わせ | BR8・BR11 |

通底しているのは「**AI は助言し、人間が決める。そしてその境界を、コードの善意ではなく認可基盤の構造として支える**」という考え方です。

- 手元で動かす：`make verify-hop`（委任チェーン）・`make verify-audit-service`（突き合わせと senior 限定ゲート）・`make verify-jailbreak`（脱獄・敵対的入力に対する構造的封じ込め）。UI では `http://localhost:3000` から、チャット→承認→監査画面という一連の流れを確認できます
