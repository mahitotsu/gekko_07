# 6. 送信者拘束の難しさ（DPoP / RFC 8705）

> 対象読者：ここまで全章、特に[第 2 章](02-token-exchange.md)（Impersonation と Delegation）を読んだ方。
> この章のねらい：ベアラートークンの盗難対策としての「送信者拘束」を知り、それを Impersonation 型の多段 Token Exchange に組み込もうとすると、クライアントをまたいだ再交換のところで難しさが出てくる、という点を、実際に試して分かったこととしてお伝えします。少し込み入った話ですが、順を追えば大丈夫です。

## 6.1 おさらい：ベアラートークンは盗まれると使われる

[第 1 章 1.7](01-oauth-basics.md#17-ベアラートークン便利さと弱点)で見たとおり、ベアラートークンは「持っていれば使える」ものです。トークン文字列が盗まれると、盗んだ者がそのまま正規利用者になりすませてしまいます。トークン自身には「今これを提示しているのが、発行された本人か」を確かめる術がありません。

[第 5 章](05-workload-identity.md)の mTLS は、通信路の身元を固めることで、これを**大部分**カバーします。「正しい相手としか通信しない」なら、外部の攻撃者が盗んだトークンを差し込む余地は狭くなります。ただし、mTLS でも塞ぎきれない隙間が残ります（この点は後ほど 6.6 で説明します）。そこで出てくるのが、**トークン自体を「特定の鍵の持ち主」に縛る**というアプローチ——送信者拘束（sender-constraining）です。

## 6.2 送信者拘束の 2 方式：DPoP と RFC 8705

送信者拘束は、「トークンに『これはこの鍵の持ち主専用』という印を付け、使うときにその鍵を持っていることを証明させる」という考え方です。主な方式が 2 つあります。

### DPoP（RFC 9449）

クライアントが自分で鍵ペアを作り、トークンをその公開鍵に紐づけて発行してもらいます。トークンを使うたびに、対応する秘密鍵で署名した「証明（DPoP proof）」を添えます。秘密鍵を持たない者は、トークン文字列だけを盗んでも証明を作れないので、使えません。

### RFC 8705（証明書拘束アクセストークン）

mTLS で使っているクライアント証明書のサムプリント（指紋）を、トークンの中（`cnf.x5t#S256` クレーム）に埋め込みます。トークンを使うときの mTLS 接続で提示された証明書の指紋が、トークン内の指紋と一致しなければ受け付けません。SPIFFE/SPIRE で既に mTLS をしているこのサンプルとは、相性がよさそうに見える方式です。

どちらも狙いは同じで、**盗まれたトークン文字列を、鍵（または証明書）を持たない者が再利用できないようにする**ことです。

## 6.3 このサンプルでの検証：はじめはうまくいきそうでした

このサンプルでは、この両方を実際に試しています。

- **DPoP** を 1 ホップに試験導入して実機で検証しました（[ADR 0013](../docs/adr/0013-dpop-sender-constraining.md)）が、後に mTLS との実利の重複を理由に取り外しました（[ADR 0015](../docs/adr/0015-dpop-removal-and-fraud-detection-engine-mtls.md)）
- mTLS を全ホップに広げ終えた後、もう一方の **RFC 8705** を、使い捨ての環境で再検証しました（[ADR 0048](../docs/adr/0048-sender-constraining-terminal-hop-only.md)）

RFC 8705 の実装可能性については、前向きな感触でした。発行側は Envoy が持つ証明書指紋を Keycloak が期待する形に整えるだけ（約 30 行の文字列整形で足りました）、検証側も Envoy のフィンガープリントヘッダーとの数行の文字列比較で済みます。暗号処理を自前で実装する必要はありませんでした。「安価に実装できそうだ」というところまでは確認できたのです。

**ところが、委任チェーンに組み込もうとしたところで、壁にぶつかりました。**

## 6.4 核心：Impersonation 型の多段 Token Exchange で、送信者拘束済みトークンの再交換が難しい理由

3 つのクライアントからなる委任チェーンで、既に送信者拘束された `subject_token` を、**別のクライアント（別の鍵・別の証明書）が次のホップへ再 exchange しようとすると、Keycloak が拒否します**。エラーメッセージは次のとおりでした。

```
Sender-constrained token exchange rejected as the token was not issued for the requesting client
```

これは DPoP でも RFC 8705 でも一字一句同じでした。Keycloak のこの拒否は、いくつかの仕様のかみ合わせ方を考えると「なるほど、そう振る舞うのが自然だ」と納得できるものでした（[ADR 0048](../docs/adr/0048-sender-constraining-terminal-hop-only.md)）。順を追って説明します。

**① 送信者拘束は「秘密鍵を今持っていること」を求めています。**
DPoP（[RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html)）が暗号的に証明するのは、正確には「その人が誰か」という身元ではなく、「**このトークンが拘束された公開鍵に対応する秘密鍵を、今まさに提示している者が保持している**」という事実です（鍵の所持の証明。key possession）。トークンを使うたびに、その鍵で署名した証明を添えることで、これを示します。「身元の一致」というより「鍵の所持の一致」を求める、という点がこの後の議論で効いてきます。

**② Impersonation 方式は、誰が代理しているかを記録しません。**
[第 2 章 2.5](02-token-exchange.md#25-impersonation-と-delegation委任の-2-つのモデル)で見たとおり、Impersonation 方式（[RFC 8693](https://www.rfc-editor.org/rfc/rfc8693.html)）は、交換後のトークンを「元の主体そのもの」として扱い、「実際に今それを提示しているのが誰か」（`act` クレーム）を**記録しません**。誰が代理しているかを、意図的に追跡しない設計です。

**③ すると、「別のクライアントへ拘束し直してよい」という認可の根拠が、どこにもありません。**
ここが核心です。送信者 A の鍵に拘束されたトークンを、別のクライアント B が受け取って「B の鍵に付け替えて（re-bind して）」次へ渡してよいでしょうか。それを許してよいと判断するには、認可サーバーが「B は、この主体の代理（actor）として振る舞ってよい相手だ」と**独立に認可できる根拠**を持っていなければなりません。ところが Impersonation 方式は、まさにその「誰が代理しているか」を記録も判定もしない設計なので、B を actor として認可するための拠り所がそもそも存在しません。

拠り所がないまま Keycloak が黙って付け替えを許してしまうと、送信者拘束の意味が消えてしまいます——攻撃者が盗んだ拘束済みトークンを、Token Exchange で「自分の鍵に付け替えて」正当化できてしまい、「盗まれたトークンの再利用を防ぐ」という目的そのものが崩れるからです。ですから、Impersonation 型のクライアントをまたぐ交換では、Keycloak が拒否するのは**安全側に倒すための自然な選択**だと言えます。図にすると次のようになります。

```
送信者 A の鍵に拘束されたトークン
        │
        ▼
   クライアント B が exchange を要求

   問い：「A 用のトークンを B 用に拘束し直してよい」
         という認可の根拠はどこにあるか？

   ┌─ Impersonation のみ ──────────────┐
   │  誰が代理か（actor）を記録・判定しない  │
   │        ↓                            │
   │  B を actor として認可する根拠がない    │
   │        ↓                            │
   │  拒否（安全側）← 今回観測した挙動        │
   └────────────────────────────────┘

   ┌─ Delegation（subject_token + actor_token + may_act）┐
   │  AS が B を actor として独立に認可できる              │
   │        ↓                                          │
   │  安全な再拘束を「設計できる」土台がある                 │
   └──────────────────────────────────────────┘
```

### この帰結：終端ホップにしか安全に適用できない

したがって、Impersonation 方式のもとでは、DPoP も RFC 8705 も、**その後に再 exchange されない「終端ホップ」**にしか安全に設定できません。委任チェーンの途中のホップに送信者拘束をかけると、次のホップでの再交換が拒否され、チェーンが途切れてしまいます。

言い換えると、送信者拘束で「委任チェーン全体のトークン窃取を塞ぐ」という広い効果は、**Impersonation 方式を採っている限りは得られない**、ということになります。守れるのは、各終端ホップ単体だけです。

> **どの仕様も「必ず拒否せよ」と決めているわけではありません。** RFC 8693 は、交換されるトークン自体の「構文・意味・セキュリティ特性（送信者拘束を含む）は明示的にスコープ外」だとしていて、PoP をどう扱うかは追加のプロファイルやデプロイ方針に委ねています。また RFC 8693 は `actor_token` と `may_act` によって、認可サーバーが actor を独立に認可するモデル（＝ Delegation）も用意しています。一方 RFC 9449（DPoP）は、DPoP をトークンリクエスト一般（extension grant を含む）に適用できると定めてはいますが、Token Exchange で**別のクライアント／actor へ移るときに、入力トークンの既存の拘束をどう継承・再拘束するか**については何も定義していません（Token Exchange や delegation という語自体、一度も出てきません）。つまり、**「Impersonation 型のクライアントをまたぐ交換で、拘束済みトークンを安全に付け替えるための一般的な意味づけ（semantics）が、どの仕様にも定義されていない」**というのが正確なところです。だから安全側に倒して拒否する、という Keycloak の選択は理にかなっています。実際、Keycloak には「DPoP 拘束済みトークンと delegation を同時に使いたい」という未解決の機能要望 issue（[#51205](https://github.com/keycloak/keycloak/issues/51205)）も立っています。仕様書を個別に読んでいるだけでは気づきにくいところで、実際に組み合わせて動かしてみて、初めてはっきり見えた部分でした。

## 6.5 Delegation なら、安全な再拘束を設計するための根拠を持てる——ただし代わりにはならない

「では、[第 2 章](02-token-exchange.md)の Delegation 方式（`actor_token`＋`act` クレーム）ならどうでしょうか」——これは鋭い問いです。答えは「Delegation なら、安全な再拘束を設計するための土台（根拠）を持てます」です。ただし、それだけで送信者拘束の意味づけが自動的に完成する、というわけではありません。

Delegation 方式では、各ホップが**自分自身を表す `actor_token`**（そのホップの actor が誰かを示す、通常のアクセストークン）を提示します。`act` クレームが「誰が代理したか」を明示的に記録し、認可サーバーは `may_act` 等で「この actor を認めてよいか」を独立に判定できます。つまり 6.4 の③で「存在しない」と述べた**認可の根拠**（誰を actor として認めるか）を、Delegation は持てるのです。そのうえで送信者拘束を重ねるなら、各ホップが**そのトークンに拘束された鍵に対応する秘密鍵を所持していること**を PoP（proof-of-possession）で別途証明する、という形になります。ここで大事なのは、「誰が actor か（`actor_token` が示すこと）」と「拘束された鍵を所持しているか（PoP が示すこと）」は別々の関心事だという点です。Delegation はこの 2 つを各ホップ内で分けて完結させ、ホップ間の連鎖を `act` の入れ子で表現できる——という設計の余地を生みます。

ただし注意したいのは、RFC 8693 は「送信者拘束をホップ間でどう継承・再拘束するか」そのものを規定しているわけではない、という点です。ですから「actor を認可できる ＝ 送信者拘束の意味づけまで自動的に完成する」とは限りません。Delegation は、あくまで**安全な再拘束を設計するための出発点になりうる**、という位置づけです。

ただ、Delegation は、送信者拘束のためだけに採るには、コストが 2 つあります（[ADR 0048](../docs/adr/0048-sender-constraining-terminal-hop-only.md)）。

1. **トークンの肥大化**：`act` クレームはホップごとに入れ子になり、委任チェーンが長いほど JWT が線形に大きくなっていきます
2. **Keycloak の機能成熟度**：`act` の生成に必要な `token-exchange-delegation` は、Keycloak の成熟度区分で最も低い "Experimental" です

加えて、このサンプルの監査の仕組み（[第 4 章 4.5](04-ai-agent-identity.md#45-説明責任非決定的な-ai-を決定的に確かめる)）は、Impersonation の「`sub` が本人のまま」を前提に組み立てています。Delegation への切り替えは、監査の作り直しまで伴います。ですので、送信者拘束の制約を回避したいという目的だけで選ぶ手ではない、と判断しています。

## 6.6 結論：現時点では導入していません

このサンプルでは、DPoP・RFC 8705 のどちらも**現時点では導入していません**（[ADR 0048](../docs/adr/0048-sender-constraining-terminal-hop-only.md)）。理由を整理すると、次のとおりです。

- 効果が、各**終端ホップ単体**に限られます（6.4 の構造的な制約）
- その範囲の**大部分は、既に mTLS が守っています**（[第 5 章](05-workload-identity.md)）
- 残る「隙間」は狭いものです：mTLS が守るのは通信路の呼び出し元の身元であって、トークンの再利用そのものではありません。たとえば account-service は、複数の正規の呼び出し元（fraud-mcp-server・fraud-detection-engine・frontend・audit-service）からの mTLS を受けます。この構成では、「**ある正規の呼び出し元が漏らしたトークンを、（万一侵害された）別の正規の呼び出し元が同じ account-service へ提示する**」という横方向の再利用は、mTLS では止まりません。証明書拘束であれば `cnf` の不一致で止まります。ただし、この残りの脅威は狭く、効果も終端ホップ単体に限られるため、現時点では投資に見合わない、と判断しました

念のため補足すると、これは「よく分からないので見送った」ということではありません。実際に動かしてみて、さらに仕様まで遡って「なぜ効果が終端ホップに限られるのか」を確かめたうえでの判断です。将来、「終端ホップ単体のトークン窃取まで防ぎたい」という要求がはっきりしてくれば、「安価に実装できそうだ」という確認済みの感触を出発点に、あらためて評価できます（未決の問いは [docs/architecture.md](../docs/architecture.md) §11 に残しています）。

## 6.7 この章のまとめ

- ベアラートークンの盗難・再利用を**トークン自体で**防ぐのが送信者拘束です。方式は DPoP（RFC 9449）と RFC 8705（証明書拘束）の 2 つがあります
- このサンプルでは両方を実機で試し、実装は安価そうだと確認できました
- ただし、**Impersonation 型のクライアントをまたぐ交換では、拘束済みトークンを安全に付け替える（再拘束する）ための認可の根拠がありません**：送信者拘束は「トークンに拘束された鍵に対応する秘密鍵の所持」を求めるのに対し、Impersonation は誰が代理しているかを記録しないため、別クライアントを actor として認可する拠り所を持ちません。だから Keycloak は再交換を拒否します（安全側の自然な選択です）
- その結果、Impersonation 方式のもとでは、送信者拘束は**再 exchange されない終端ホップにしか安全に適用できません**。どの仕様も「必ず拒否せよ」とは決めておらず、正確には「クライアントをまたぐ安全な再拘束の意味づけが、どの仕様にも定義されていない」という**仕様間のギャップ**です
- Delegation 方式なら、安全な再拘束を設計するための根拠（`actor_token`／`may_act`）を持てます。ただしそれだけで意味づけが完成するわけではなく、加えてトークンの肥大化・機能成熟度・監査設計の作り直し、というコストもかかります
- 結論として、mTLS が大部分を守っており、残りが狭いことから、現時点では導入していません。根拠を確かめたうえでの見送りです
