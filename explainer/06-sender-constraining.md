# 6. 送信者拘束の難しさ（DPoP / RFC 8705）

> 対象読者：ここまで全章、特に[第 2 章](02-token-exchange.md)（Impersonation と Delegation）を読んだ方。
> この章のねらい：ベアラートークンの盗難対策としての「送信者拘束」を知り、それが Token Exchange（Impersonation 方式）と組み合わさると仕様レベルで難しくなる、という点を、実際に試して分かったこととしてお伝えします。少し込み入った話ですが、順を追えば大丈夫です。

## 6.1 おさらい：ベアラートークンは盗まれると使われる

[第 1 章 1.7](01-oauth-basics.md#17-ベアラートークン便利さと弱点)で見たとおり、ベアラートークンは「持っていれば使える」ものです。トークン文字列が盗まれると、盗んだ者がそのまま正規利用者になりすませてしまいます。トークン自身には「今これを提示しているのが、発行された本人か」を確かめる術がありません。

[第 5 章](05-workload-identity.md)の mTLS は、通信路の身元を固めることで、これを**大部分**カバーします。「正しい相手としか通信しない」なら、外部の攻撃者が盗んだトークンを差し込む余地は狭くなります。ただし、mTLS でも塞ぎきれない隙間が残ります（この点は後ほど 6.5 で説明します）。そこで出てくるのが、**トークン自体を「特定の鍵の持ち主」に縛る**というアプローチ——送信者拘束（sender-constraining）です。

## 6.2 送信者拘束の 2 方式：DPoP と RFC 8705

送信者拘束は、「トークンに『これはこの鍵の持ち主専用』という印を付け、使うときにその鍵を持っていることを証明させる」という考え方です。主な方式が 2 つあります。

### DPoP（RFC 9449）

クライアントが自分で鍵ペアを作り、トークンをその公開鍵に紐づけて発行してもらいます。トークンを使うたびに、対応する秘密鍵で署名した「証明（DPoP proof）」を添えます。秘密鍵を持たない者は、トークン文字列だけを盗んでも証明を作れないので、使えません。

### RFC 8705（証明書拘束アクセストークン）

mTLS で使っているクライアント証明書のサムプリント（指紋）を、トークンの中（`cnf.x5t#S256` クレーム）に埋め込みます。トークンを使うときの mTLS 接続で提示された証明書の指紋が、トークン内の指紋と一致しなければ受け付けません。SPIFFE/SPIRE で既に mTLS をしているこのサンプルとは、相性がよさそうに見える方式です。

どちらも狙いは同じで、**盗まれたトークン文字列を、鍵（または証明書）を持たない者が再利用できないようにする**ことです。

## 6.3 このサンプルでの検証：はじめはうまくいきそうでした

このサンプルでは、この両方を実際に試しています。

- **DPoP** を 1 ホップに試験導入して実機で検証しました（[ADR 0013](../docs/adr/0013-dpop-sender-constraining.md)）が、後に mTLS との実利の重複を理由に取り外しました（[ADR 0015](../docs/adr/0015-dpop-removal-and-fraud-detection-engine-mtls.md)）
- mTLS を全ホップに広げ終えた後、もう一方の **RFC 8705** を、使い捨ての環境で再検証しました（[ADR 0048](../docs/adr/0048-sender-constraining-terminal-hop-only.md)）

RFC 8705 の実装可能性については、前向きな感触でした。発行側は Envoy が持つ証明書指紋を Keycloak が期待する形に整えるだけ（約 30 行の文字列整形で足りました）、検証側も Envoy のフィンガープリントヘッダーとの数行の文字列比較で済みます。暗号処理を自前で実装する必要はありませんでした。「安価に実装できそうだ」というところまでは確認できたのです。

**ところが、委任チェーンに組み込もうとしたところで、壁にぶつかりました。**

## 6.4 核心：送信者拘束と Impersonation 方式の Token Exchange は両立しない

3 つのクライアントからなる委任チェーンで、既に送信者拘束された `subject_token` を、**別のクライアント（別の鍵・別の証明書）が次のホップへ再 exchange しようとすると、Keycloak が拒否します**。エラーメッセージは次のとおりでした。

```
Sender-constrained token exchange rejected as the token was not issued for the requesting client
```

これは DPoP でも RFC 8705 でも一字一句同じでした。ということは、Keycloak の実装都合というより、もっと根の深い理由がありそうです。調べてみると、これは**関連する複数の RFC の定義を重ね合わせると論理的に導ける、構造的な帰結**だと分かりました（[ADR 0048](../docs/adr/0048-sender-constraining-terminal-hop-only.md)）。順を追って説明します。

**① 送信者拘束の定義は「鍵の保持者の同一性」を求めています。**
DPoP（[RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html)）は、「トークンの正当な提示者は、鍵ペアの秘密鍵を保持し、それを証明する送信者に限定される」と定義しています。つまり「正当な提示者 ＝ 発行時に鍵の所有を証明したのと**同一の主体**」であることが、定義上の前提になっています。

**② RFC 8693 の Impersonation 方式は、提示者の同一性をあえて消しています。**
[第 2 章 2.5](02-token-exchange.md#25-impersonation-と-delegation委任の-2-つのモデル)で見たとおり、Impersonation 方式（[RFC 8693](https://www.rfc-editor.org/rfc/rfc8693.html)）は、交換後のトークンを「元の主体そのもの」として扱い、「実際に今それを提示しているのが誰か」（`act` クレーム）を**記録しません**。誰が代理しているかを、意図的に追跡しない設計です。

**③ ①と②を重ねると、両立しなくなります。**
送信者拘束は「今この鍵を持つ者だけが正当な提示者だ」と言い、Impersonation は「元の主体とは別の実体が、その区別を記録せずに正当な提示者として振る舞ってよい」と言います。この両方を同時に満たそうとすると、整合する解釈は「**拘束済みの `subject_token` を、別の鍵の持ち主が再 exchange するのを拒否する**」以外になくなります。

もしここで Keycloak が黙って「新しい鍵に付け替える（re-bind）」ことを許してしまうと、送信者拘束の意味が消えてしまいます——攻撃者が盗んだ拘束済みトークンを、Token Exchange で「自分の鍵に付け替えて」正当化できてしまい、「盗まれたトークンの再利用を防ぐ」という目的そのものが崩れてしまうからです。ですから、Keycloak が拒否するのは、Impersonation 方式のもとでは**安全側に倒すための、自然な選択**だと言えます。

### この帰結：終端ホップにしか適用できない

したがって、DPoP も RFC 8705 も、**その後に再 exchange されない「終端ホップ」**にしか安全に設定できません。委任チェーンの途中のホップに送信者拘束をかけると、次のホップでの再 exchange が拒否され、チェーンが途切れてしまいます。

言い換えると、送信者拘束で「委任チェーン全体のトークン窃取を塞ぐ」という広い効果は、**Impersonation 方式を採っている限り、原理的に得られない**、ということになります。守れるのは、各終端ホップ単体だけです。

> **この点は、どの RFC にも書かれていません。** RFC 8693 は送信者拘束（cnf）について何も規定しておらず、RFC 9449 は Token Exchange や delegation という語を一度も使っていません。それぞれの仕様は自己完結して正しいのに、**組み合わせたときに初めて表に出てくる仕様間のギャップ**なのです。実際、Keycloak には「DPoP 拘束済みトークンと delegation を同時に使いたい」という未解決の機能要望 issue（[#51205](https://github.com/keycloak/keycloak/issues/51205)）が立っており、このニーズが未解決のまま残っていることがうかがえます。仕様書を個別に読んでいるだけでは気づきにくいところで、実際に動かしてみて再現できたことで、初めて言葉にできた部分でした。

## 6.5 Delegation 方式なら両立する——ただし代わりにはならない

「では、[第 2 章](02-token-exchange.md)の Delegation 方式（`actor_token`＋`act` クレーム）ならどうでしょうか」——これは鋭い問いで、答えは「原理的には両立します」です。

Delegation 方式では、各ホップが「自分自身の鍵で、自分自身の `actor_token` を提示する」ことになります。`act` クレームが「誰が代理したか」を明示的に記録するので、6.4 の①②の食い違い（提示者の同一性を消してしまう問題）が生じません。各ホップの中で「鍵の保持者の同一性」が完結し、ホップ間の連鎖は `act` の入れ子で表現されます。ですから、再 bind も原理的に成り立ちます。

ただ、Delegation は、送信者拘束のためだけに採るには、コストが 2 つあります（[ADR 0048](../docs/adr/0048-sender-constraining-terminal-hop-only.md)）。

1. **トークンの肥大化**：`act` クレームはホップごとに入れ子になり、委任チェーンが長いほど JWT が線形に大きくなっていきます
2. **Keycloak の機能成熟度**：`act` の生成に必要な `token-exchange-delegation` は、Keycloak の成熟度区分で最も低い "Experimental" です

加えて、このサンプルの監査の仕組み（[第 4 章 4.5](04-ai-agent-identity.md#45-説明責任非決定的な-ai-を決定的に確かめる)）は、Impersonation の「`sub` が本人のまま」を前提に組み立てています。Delegation への切り替えは、監査の作り直しまで伴います。ですので、送信者拘束の制約を回避したいという目的だけで選ぶ手ではない、と判断しています。

## 6.6 結論：現時点では導入していません

このサンプルでは、DPoP・RFC 8705 のどちらも**現時点では導入していません**（[ADR 0048](../docs/adr/0048-sender-constraining-terminal-hop-only.md)）。理由を整理すると、次のとおりです。

- 効果が、各**終端ホップ単体**に限られます（6.4 の構造的な制約）
- その範囲の**大部分は、既に mTLS が守っています**（[第 5 章](05-workload-identity.md)）
- 残る「隙間」は狭いものです：mTLS が守るのは通信路の呼び出し元の身元であって、トークンの再利用そのものではありません。たとえば account-service は、複数の正規の呼び出し元（fraud-mcp-server・frontend など）からの mTLS を受けます。この構成では、「**ある正規の呼び出し元が漏らしたトークンを、（万一侵害された）別の正規の呼び出し元が同じ account-service へ提示する**」という横方向の再利用は、mTLS では止まりません。証明書拘束であれば `cnf` の不一致で止まります。ただし、この残りの脅威は狭く、効果も終端ホップ単体に限られるため、現時点では投資に見合わない、と判断しました

念のため補足すると、これは「よく分からないので見送った」ということではありません。実際に動かしてみて、さらに仕様まで遡って「なぜ効果が終端ホップに限られるのか」を確かめたうえでの判断です。将来、「終端ホップ単体のトークン窃取まで防ぎたい」という要求がはっきりしてくれば、「安価に実装できそうだ」という確認済みの感触を出発点に、あらためて評価できます（未決の問いは [docs/architecture.md](../docs/architecture.md) §11 に残しています）。

## 6.7 この章のまとめ

- ベアラートークンの盗難・再利用を**トークン自体で**防ぐのが送信者拘束です。方式は DPoP（RFC 9449）と RFC 8705（証明書拘束）の 2 つがあります
- このサンプルでは両方を実機で試し、実装は安価そうだと確認できました
- ただし、**Impersonation 方式の Token Exchange とは両立しません**：送信者拘束は「鍵の保持者の同一性」を求めるのに対し、Impersonation は提示者の同一性を消します。重ねると、拘束済みトークンの再 exchange は拒否せざるを得なくなります（安全側の自然な帰結です）
- その結果、送信者拘束は**再 exchange されない終端ホップにしか適用できません**。これはどの RFC にも明記されていない**仕様間のギャップ**です
- Delegation 方式なら原理的に両立しますが、トークンの肥大化・機能成熟度・監査設計の作り直し、というコストの方が大きくなります
- 結論として、mTLS が大部分を守っており、残りが狭いことから、現時点では導入していません。根拠を確かめたうえでの見送りです
