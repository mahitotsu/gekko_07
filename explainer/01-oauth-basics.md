# 1. OAuth 2.0 の基礎

> 対象読者：OAuth 2.0 を初めて学ぶ方。以降の解説（特に Token Exchange）で使う用語を、ここで一緒に揃えていきます。
> 前提知識：HTTP の基本（リクエスト・ヘッダー）だけで大丈夫です。

## 1.1 そもそも、なぜ「トークン」が要るのか

社内システムに「アナリストの田中さん」がログインして、口座情報を見る場面を考えてみます。素朴に考えると、田中さんのパスワードをアプリに預け、アプリがそれを使って各サービスにアクセスすればよさそうに思えます。ですが、これは避けたいやり方です。理由は次のとおりです。

- パスワードを預かったアプリは、田中さんの**全権限**を持つことになります。口座を見るだけのつもりでも、原理的には何でもできてしまいます
- パスワードが漏れてしまうと、有効期限もなく、範囲の限定もないまま、悪用され続けてしまいます
- 「田中さんの代理で口座**照会だけ**を行う」といった、権限を絞った預け方ができません

OAuth 2.0 は、この問題を「パスワードの代わりに、**用途と期限を限定したトークン**を発行して渡す」という形で解決します。トークンは、「この持ち主は、この範囲の操作を、この期限まで行ってよい」という許可証のようなもの、と考えていただくと分かりやすいと思います。

このサンプルでも、アナリストのパスワードがマイクロサービス群に流れることはありません。パスワードは認可サーバー（後述します）にログインするときだけ使い、それ以降はトークンだけがやり取りされます。

> **OAuth と OIDC の関係について（先に一言）**：厳密には、ユーザーの「ログイン（あなたは誰か）」には OpenID Connect（OIDC）を、その後の「API 認可（何をしてよいか）」には OAuth 2.0 のアクセストークンを使っています。OIDC は OAuth 2.0 の上に本人確認の層を足した規格、という関係です。このサンプルの主題は Token Exchange（OAuth 側）なので、この解説では以降 OAuth 側を中心に説明します。「ログインは OIDC、API 権限は OAuth」とだけ頭の隅に置いておいていただければ十分です。

## 1.2 登場人物

OAuth には決まった役者がいます。このサンプルの例で対応づけてみます。

| OAuth の役割 | 意味 | このサンプルでの例 |
|---|---|---|
| **リソースオーナー** | 保護されたリソースへのアクセスを認可できる主体（＝アクセスを許可する権限を持つ人）。多くは人間です | アナリスト（田中さん） |
| **クライアント** | リソースオーナーの代わりにデータへアクセスしたいアプリ | frontend（アナリスト向け画面） |
| **認可サーバー**（AS） | 本人確認をして、トークンを発行します。OAuth の心臓部です | Keycloak |
| **リソースサーバー** | トークンを検証し、正しければデータを返します | account-service（口座・取引を持つサービス） |

「リソースオーナー」は「データの所有者」という意味ではなく、「そのアクセスを認可できる立場の人」を指す点に注意してください。この解説では、アナリスト本人が持つ権限を起点にして説明していきます。

認可サーバー（Keycloak）と、リソースサーバー（account-service など）が別々である点が大切です。**トークンを「発行する側」と「検証して使わせる側」が分かれている**からこそ、後で出てくる「委任」や「権限の絞り込み」が成り立ちます。

## 1.3 アクセストークンに書かれていること

OAuth で発行されるトークンにはいくつか種類がありますが、まず押さえたいのは**アクセストークン**（リソースへアクセスするための許可証）です。このサンプルでは JWT（JSON Web Token）という形式のアクセストークンを使います。JWT は「署名付きの JSON」で、中身を覗くと次のような主張（クレーム）が入っています。

このサンプルでアナリストがログインしたときに発行される**ログイントークン**を例にすると、次のようになります。

| クレーム | 値の例 | 意味 |
|---|---|---|
| `sub` | `a1b2c3...`（アナリストの一意 ID） | **誰の**トークンか（subject）。この人が誰であるかの一次識別子です |
| `iss` | Keycloak の realm URL | **誰が**発行したか（issuer）。信頼できる発行者かを検証します |
| `aud` | `frontend` | **誰宛て**のトークンか（audience）。このトークンを受け取ってよい相手です |
| `exp` | Unix 時刻 | いつ**失効**するか。期限切れのトークンは拒否されます |
| `scope` | `openid` | 何を**してよい**か（権限の範囲） |

このうち `sub`・`aud`・`scope` の 3 つは、以降の解説で繰り返し登場します。それぞれ「誰の」「誰宛ての」「何をしてよい」トークンか、と覚えておいていただければ十分です。

> **`openid` という scope について**：上の例の `scope=openid` は、業務上の権限ではなく、「OIDC（本人確認）の機能を使いますよ」とプロトコルへ要求するための特別なスコープです。後で出てくる `account:read`（口座を読んでよい）のような業務権限のスコープとは、少し性格が違います。ログイントークンの時点では、まだ業務権限のスコープは付いていない、と考えてください（この点は [1.4](#14-audienceaudこのトークンは誰宛てか) で改めて触れます）。

> **なぜ署名が要るのか**：JWT は Base64 で符号化されているだけで、暗号化ではありません。中身は誰でも読めます。ただし認可サーバーの秘密鍵で**署名**されているため、リソースサーバーは対応する公開鍵を使って「これは確かに Keycloak が発行し、改ざんされていない」ことを確認できます。中身を書き換えると署名が壊れ、検証で弾かれる仕組みです。

## 1.4 audience（`aud`）：「このトークンは誰宛てか」

`aud` は初めて学ぶときに見落としやすいのですが、このサンプルの設計では主役級に重要なので、少し丁寧に説明します。

`aud` は「このトークンを受け取ってよいのは誰か」を示します。account-service は、自分に届いたトークンの `aud` が `account-service` であることを確認してから処理します。もし `aud=frontend` のトークンが account-service に届いた場合は、「これは私宛てではない」として受け付けません。

これがなぜ大切かというと、**`aud` チェックがないと、あるサービス向けに発行されたトークンを、別のサービスで使い回せてしまう**からです。たとえば「田中さんが frontend にログインするために発行されたトークン」を、そのまま account-service に投げて口座を読めてしまうと、権限の範囲が意味をなさなくなります。`aud` は「トークンの通用範囲」を 1 つのサービスに閉じ込めるための仕組みです。

このサンプルでは「**トークンは常に単一の audience しか持たない**」という原則を採っています（[ADR 0005](../docs/adr/0005-single-audience-tokens-only.md)）。ログイントークンは `aud=frontend` だけを持ち、`account:read` のような権限は一切含みません。frontend が account-service を呼びたくなったら、その都度「account-service 宛ての別のトークン」を取り直します。この「取り直し」こそが次章で扱う Token Exchange であり、単一 audience 原則がなぜ大切なのかは[第 2 章](02-token-exchange.md)で腑に落ちると思います。

## 1.5 scope：「何をしてよいか」

`scope` は権限の範囲を表す文字列です。このサンプルでは、業務操作ごとにスコープを分けています。

| スコープ | 意味 |
|---|---|
| `account:read` | 口座・取引の**読み取り** |
| `account:propose` | 凍結解除の**提案**（記録するだけ。取り消せる・低リスク） |
| `account:unfreeze` | 凍結解除の**実行**（取り消せない・高リスク） |

同じ account-service に対する操作でも、「読む」「提案する」「実行する」でスコープが違います。account-service は、届いたトークンの `scope` を見て「このトークンで、この API を呼んでよいか」を判定します。`account:read` しか持たないトークンで凍結解除 API を呼ぼうとすれば、受け付けられません。

このスコープの分け方が、後の「AI エージェントに実行権限を渡さない」仕掛けの土台になります。AI エージェントが持てるトークンには `account:unfreeze` を**構造的に含めない**——その具体的なやり方は[第 3 章](03-scope-and-audience-topology.md)で扱います。

## 1.6 トークンの取得：認可コードフロー + PKCE

では、アナリストがログインすると、トークンはどのように発行されるのでしょうか。このサンプルは、OAuth の標準的な取得方法である**認可コードフロー（Authorization Code Flow）に PKCE を足したもの**を使います（[ADR 0031](../docs/adr/0031-frontend-implementation.md)）。流れは次のとおりです。

1. アナリストが frontend にアクセスすると、Keycloak のログイン画面へリダイレクトされます
2. アナリストが Keycloak でパスワードを入力します（**パスワードは Keycloak にしか渡りません**。frontend は見ません）
3. 認証に成功すると、Keycloak は frontend に短命の「**認可コード**」を返します（トークンそのものではなく、引換券のようなものです）
4. frontend は裏側（サーバー間通信）で、その認可コードを Keycloak のトークンエンドポイントに送り、**アクセストークンに引き換えます**

なぜ「コードを一旦返して、裏で引き換える」という二段構えにするのでしょうか。トークンを直接ブラウザの URL に載せて返すと、ブラウザ履歴・リファラ・ログにトークンが残ってしまう恐れがあります。認可コードは一度きり・短命で、frontend（自分の身元を Keycloak に証明できるクライアント）だけが引き換えられるため、仮に漏れても悪用されにくい、という考え方です。

**PKCE**（Proof Key for Code Exchange）は、この認可コードの横取りをさらに防ぐための追加の仕掛けです。frontend は最初に秘密の乱数（code_verifier）を作り、そのハッシュ（code_challenge）だけを手順 1 で Keycloak に預けておきます。手順 4 で認可コードを引き換えるときに、元の乱数（code_verifier）を提示します。攻撃者が認可コードだけを盗んでも、元の乱数を知らないので引き換えられない、という仕組みです。

> このサンプルではさらに、この認可コードの受け渡し（コールバック）を `response_mode=form_post` にして、コードや state を URL に一切載せないようにしています（[ADR 0032](../docs/adr/0032-frontend-oidc-callback-form-post.md)）。ここは応用的な話なので、まずは「ログイン＝認可コードフロー + PKCE でトークンを得る」とだけ押さえていただければ十分です。

## 1.7 ベアラートークン：便利さと弱点

こうして得たアクセストークンを、クライアントは HTTP リクエストのヘッダーに載せてリソースサーバーへ送ります。

```
GET /accounts/123/transactions HTTP/1.1
Host: account-service
Authorization: Bearer eyJhbGciOi...（JWT）
```

`Bearer` は「持参人」という意味で、この方式を**ベアラートークン**と呼びます。名前のとおり、「**そのトークン文字列を持っている者は、誰であっても正当な持ち主として扱われる**」方式です。現金の紙幣と同じで、持っていれば使えます。

これは実装が単純で便利な一方、正直に言えば弱点もあります。**トークン文字列が盗まれると、盗んだ者がそのまま正規の利用者になりすませてしまう**という点です。トークン自身には「本当にこれを発行された本人が、今持っているのか」を確かめる術がありません。

この弱点にどう向き合うかは、このサンプルで確かめたかったことの一つです。対処の手立ては 2 つあります。

- **通信路の身元を固める**：そもそも「正しい相手」としか通信させないようにします（mTLS）。→ [第 5 章](05-workload-identity.md)
- **トークン自体を持ち主に縛る**：トークンを特定の鍵の持ち主にだけ使えるようにします（送信者拘束、DPoP / RFC 8705）。→ [第 6 章](06-sender-constraining.md)

第 6 章では、この「送信者拘束」が Token Exchange と組み合わさると仕様レベルで難しくなる、という点まで、実際に試して分かったことをお伝えします。

## 1.8 この章のまとめ

- OAuth はパスワードの代わりに、**用途（scope）・宛先（aud）・期限（exp）を限定したトークン**を渡す仕組みです
- トークンを**発行する側（認可サーバー = Keycloak）**と、**検証して使わせる側（リソースサーバー = account-service など）**が分かれています
- `sub`（誰の）・`aud`（誰宛て）・`scope`（何をしてよい）が、以降の主役です
- このサンプルは「トークンは常に単一 audience」を原則にしています（[ADR 0005](../docs/adr/0005-single-audience-tokens-only.md)）
- ベアラートークンは「持っていれば使える」ため、盗難には弱いです。その対策が第 5・6 章のテーマです

次章では、この「単一 audience のトークン」を、サービスをまたいで委任していく仕組み——**Token Exchange**——を扱います。
